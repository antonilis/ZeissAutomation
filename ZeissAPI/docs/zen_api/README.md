# ZEN scripting API — reference for World A

What a `.czmac` macro can actually call. Everything here lives in **World A** (IronPython 2.7
inside ZEN); none of it exists in World B. See the two-runtime rule in the project `CLAUDE.md`.

## Where this came from

Generated by [`dump_zen_api.czmac`](../../diagnostics/dump_zen_api.czmac), which walks the .NET type graph by
reflection — it never calls a method and never reads a property, so it cannot move the stage or
touch an experiment. Run it again after a ZEN upgrade and diff the output.

| | |
|---|---|
| ZEN version | 3.28 (`Zeiss.Micro.*, Version=3.28.25090.90`) |
| Assemblies scanned | 568 |
| Types described | 1636 |
| Walk depth | 6 hops from the injected names |

Depth 6 is a real limit: a type reachable only through seven or more hops is absent from the dump,
not absent from ZEN. The type cap (2000) was **not** hit, so within that depth the listing is complete.

## The one object

ZEN injects about 500 names into the macro scope — every `Zen*` enum, every `IZen*` interface, plus
`clr`, `sys`, `AppDomain`, and `System.IO`'s `Directory`, `File` and `Path`. Only a handful matter.
Everything you drive hangs off `Zen`:

```
Zen
├── Application    ZenBlueApplication   documents, folders, macros, dialogs        → gui.md
├── Acquisition    ZenBlueAcquisition   experiments, live, snap, autofocus         → acquisition.md
├── Devices        ZenDevicesLM         stage, focus, changers, lamp, camera       → devices.md
├── Processing     ZenProcessingLM      filters, segmentation, stitching, export   → processing.md
├── Analyzing      ZenAnalyzer          image analysis, regions, result tables     → analysis.md
├── Measurement    ZenMeasurement       interactive measurement, feature sets      → analysis.md
└── Windows        ZenBlueWindows       dialogs built from a macro                 → gui.md
```

`Zen` itself is a `ZenBlueScriptingWrapperServiceLM`. The `LM` suffix recurs throughout: it means
*light microscopy*, and an `…LM` class is the widefield/confocal subclass that adds members to a
shared base. `ZenProcessingLM.Filter`, for instance, is a `FilteringLM` that adds `EDF` and
`LocalMaxOrMin` on top of the plain `Filtering`. When the dump shows a member twice with different
return types, the `…LM` one is what you get.

## Three layers of names

Distinguishing these three explains most confusion when reading the dump.

**1. The scripting wrapper — `ZenImage`, `ZenExperiment`, `ZenHardwareSetting`, …**
Stable, documented by Zeiss, COM-visible. This is what you should use.

**2. The internal .NET object underneath — reachable through `.Core`.**
`ZenImage.Core` is an `ImageDocument`, `ZenExperiment.Core` is a `HardwareExperiment`,
`ZenTable.Core` is a `TableDocument`, `ZenBounds.Core` is a `SubsetBounds`,
`ZenGraphic.Core` is a `GraphicElement`, `Zen.Devices.Core` is an `IMicroscope`.
One exception worth remembering: **`ZenImageAnalysisSetting` exposes its internal object as `.Ias`,
not `.Core`.**

The internal layer is vastly richer — that is where the several hundred extra types in the dump
live. It is also unversioned: Zeiss can rename any of it in a service pack. Reach for it only when
the wrapper genuinely cannot express the thing, and say so in a comment at the call site.

**3. Extension methods — visible only where their namespace is imported.**
`ZenExperiment.ClearExperimentRegionsAndPositions` and about twenty siblings are not members of
`ZenExperiment` at all. They are static methods declared elsewhere, and IronPython surfaces them
only in a compilation unit that imported the declaring namespace. This is the single most confusing
behaviour in the whole API and has its own page: **[extension-methods.md](extension-methods.md)**.

The dump marks them explicitly:

```
    EXTENSION METHODS  (only visible where their namespace is imported)
        Void ClearExperimentRegionsAndPositions(ZenExperiment experiment, Int32 blockIndex)
            declared in Zeiss.Micro.LM.Scripting.ZenExperimentExtensions  (assembly Zeiss.Micro.LM.Scripting)
```

The first parameter is the extended type, so you call it as `experiment.ClearExperimentRegionsAndPositions(0)`.

## Rules that hold across the whole API

**The `interactive` flag.** Most processing functions come in four shapes:
`f(input)`, `f(input, interactive)`, `f(input, setting)`, `f(input, setting, interactive)`.
`interactive=True` opens the ZEN dialog and **blocks until a human clicks OK**. In an unattended
acquisition that is a hang, not a prompt. Always pass `False` explicitly, or use an overload
without the flag.

**Settings objects.** Anything with more than a few parameters takes a `*Setting` object obtained
from the matching `Settings` factory, not a keyword argument:

```python
setting = Zen.Processing.Filter.Settings.GaussSetting()
setting.AllChannels.SigmaX = 1.5
result = Zen.Processing.Filter.Smooth.Gauss(image, setting, False)
```

Every setting object carries `Load(name[, directory])`, `SaveAs(name[, directory])` and an `XML`
string property, so a preset tuned by hand in the GUI can be loaded by name from a macro. Settings
with per-channel parameters expose `AllChannels` (writes to all) and `GetChannel(i)`.

**Document-like objects.** `ZenExperiment`, `ZenHardwareSetting`, `ZenImageAnalysisSetting`,
`ZenDisplaySetting`, `ZenFeatureSet`, `ZenMeasurementSequenceSetting` and friends all derive from
`ZenCategorisedDocument` and therefore share:

| Member | Note |
|---|---|
| `Load(fileName[, ZenSettingDirectory])` | `User` or `Workgroup` |
| `Save()` / `SaveAs(fileName[, dir])` | |
| `SetActive()` | makes it the one the GUI shows |
| `Rename(newName[, overwrite])`, `Delete()`, `Import(overwrite)` | |
| `AddToCollection()` / `RemoveFromCollection()` | visibility in the GUI list |
| `Close([askForSave])` | `askForSave=True` blocks on a dialog |
| `Name`, `NameWithoutExtension`, `FileName`, `IsModified`, `DefaultExtension`, `DefaultSubFolder` | |

**Collections** expose `Count`, `Item[i]` (just `coll[i]`), `GetByName`, `GetByFileName`, `Contains`,
`Add`, `Delete`. Several only advertise `GetEnumeratorCOM`, but IronPython iterates them with a
plain `for` loop because they implement `IEnumerable`.

**Units.** Stage and focus positions are **micrometres**. `image.Metadata.ScalingMicron` gives
micrometres per pixel as a `ZenScaling` with `.X`, `.Y`, `.Z`. Note the contrast with World B, which
reads the raw `.czi` XML where the same quantity is stored in **metres** — that is where the
`* 1e6` factors in `data_processing/` come from. Angles are degrees.

**IronPython 2.7 constraints.** `.NET` overload resolution picks on argument type, so an `int`
where the API wants a `Double` is usually fine but an ambiguous `None` is not. Enums are passed as
`ZenPixelType.Gray16`, never as a string or an int. `out`/`ref` parameters (`Boolean& stopped` in
the dump) come back as part of a tuple — verify the exact shape on the instrument before relying
on it.
